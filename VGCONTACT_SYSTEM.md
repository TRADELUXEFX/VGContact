## 1. Goal and ground rules
- The **live Supabase database is the source of truth**. The Android app and the admin dashboard must follow it. Do not change the database to fit them.
- **Keys no longer exist.** No key feature should remain in the app or admin. (Leftover key columns in the database are harmless; see section 9.)
- The owner writes short dictated messages. Act without asking questions, make small step-by-step edits, deliver ZIPs with files at the root, and check JS syntax before delivering.

## 2. The idea in plain words
Users want more people to see their WhatsApp status. Users are put into groups of 3 once they are verified (the first task is the verification post; the daily repost comes after). The app saves other group members' phone numbers into your phone, so you and they can see each other's statuses.

Three parts:
- **Database (Supabase)** holds every rule and decision.
- **Android app** is only a screen. It asks the database for numbers and shows them.
- **Admin dashboard (`index.html`)** is the owner's control panel. Only the admin email hardcoded in `_is_admin()` may use it.

## 3. The rules
1. **Signup.** The new user is registered but placed in NO group. They are PENDING: Home shows 0/3 and the phone gets only the admin and anon numbers (plus their referrals).
   **Placement happens at the first verified repost** (trigger `place_on_repost_verified` -> `_place_on_verify` -> `_place_user_in_group`): the user goes into the lowest-numbered group with fewer than `group_size` verified members (`joined_via = 'signup'`, the default group); if none, a new group is created. A group fills at `group_size` verified members and becomes `is_full` and `is_published`. Groups therefore only hold verified users, no matter how long verification takes (changed 2026-10-01).
2. **Free viewers** = verified members of your own default group (0 while pending), shown as current / group_size (for example 1/3).
3. **Two tasks (changed 2026-10-02; column `daily_reposts.kind`).** (a) **Verification** (`kind='verify'`): the first task for a PENDING user, from the pending sheet: post the invite image + link on their status, get 30+ views, send a screenshot to the admin's WhatsApp. One per UTC day; only unverified users can submit it. (b) **Repost** (`kind='repost'`): the daily task for VERIFIED users only, from the Repost screen (the button opens the admin's WhatsApp and logs it). One per UTC day; blocked once the user has `free_repost_cap` verified `repost` rows (default 3). A user can have one row of each kind on the same day. Both start `pending`.
4. **Verify.** The admin verifies a pending row. Approving a `verify` row only verifies the user and places them in their default group (rule 1): no extra group, no streak, no leaderboard score, and it does not use the repost cap. Approving a `repost` row adds the user (`joined_via = 'added'`) to the lowest-numbered full group they are not already in. If no full group exists, they get nothing, and the verified repost still counts toward the cap. **Catch-up:** once a day `_catch_up_group_grants` gives users any group they are owed (verified `repost` rows only, capped by `free_repost_cap`, minus their `added` groups) once a full group exists.
5. **Extra viewers** = everyone in every other group the user belongs to, shown as current / max (max is the larger of group_size and the actual count, per group).
6. **Referred viewers** = users whose `referred_by` matches this user's username (case-insensitive), or is all digits and matches the last 10 digits of this user's phone. A referral typed at sign-up is only kept if it matches an existing account; otherwise `referred_by` is saved as NULL (no referral, Profile shows "None").
7. **Verified badge.** A user is VERIFIED once they have at least one verified row of either kind (`verify` or `repost`), otherwise PENDING. The verified-reposts count, the leaderboards and the admin "reposts" number count `repost` rows only.
8. **Sync** (what the phone saves): the admin number (`admin_phone`, named `admin_contact_name` or "VGContact Admin"), the optional `anon_phone` (named `anon_contact_name` or "VGContact Status"), plus other members of your groups. Group members are included only if they are not banned and have at least one verified repost themselves. Members of your groups are included as soon as they join: the group does not have to be full (changed 2026-10-01). Only BANNED users are left out of other people's lists: inactive (30+ days without a sync), paused and permission-off users stay on everyone's phone, and when they come back only they have to sync (changed 2026-10-03; group membership is permanent, nobody is removed from or re-placed in a group).
   **Referred users** (rule 6 matching) are also in the sync list (from `get_sync_contacts`), named by username, **3 levels deep** (people you referred, who they referred, who those referred), nearest first, with **no cap** on how many (changed 2026-10-02). A number is never sent twice: `get_sync_contacts` removes duplicates by the last 9 digits (priority: admin, anon, group member, referral), so someone who is both in your group and in your referral chain appears once. Banned users are not saved but the chain continues past them; no verified repost is required. The Home "Referred viewers" number still counts direct (level 1) referrals only.
   **System contacts (added 2026-10-04):** besides `admin_phone` and `anon_phone`, every active row of `system_contacts` is sent to every user on every sync, with `is_system = true` (plain name, no `VGC<N>` ending, never cleaned up). Order: admin, status, system contacts by `sort_order`, then the rest. A system number is sent once even if it is also a group member or referral; a user never gets their own number. Removing or deactivating a row stops it being sent; to delete it from phones that already saved it, use the delete list (`contact_removals`, added 2026-10-07: every sync, the app deletes any saved contact with a listed number, whatever its name, except numbers the server still sends that user). Removing a person from their last group does this automatically for a number in `system_contacts` (trigger `trg_group_member_removed`). Added by the secret version of `get_sync_contacts(uuid, text)` (SQL `add_system_contacts.sql`); no app change.
   **On the phone:** each saved group-member / referral contact is named `<name> VGC<N>` (the admin and status numbers are the exception: the server marks them `is_system` and the app saves them with their plain name, no tag, so cleanup never touches them) (e.g. `Chidera VGC3`, N = lowest free number). The `VGC<N>` ending is how the app recognises its own contacts, read from the phone itself, so it survives clearing app data. Each sync also removes VGC contacts whose number is no longer in the server list (banned or removed member); contacts without the tag are never touched by that clean-up, and an empty server list never deletes anything. The one exception is the delete list (`contact_removals`, 2026-10-07): numbers on it are deleted from the phone whatever the contact is named.
9. **Bans** block by user, phone and device (`banned_identities`). Banned users get `ACCOUNT_BANNED`.
10. **Support.** "Buy Status Viewers" opens a WhatsApp chat with support (number in `SupportContact.kt`).
11. **Account secret (added 2026-10-03, versionCode 74).** Knowing a user id is not enough to act as that user. Each account has `users.secret` (long random code), created by `register_account` / `login_account` and saved on the phone (`SessionManager.saveSecret`). Every app function that acts for a user now takes `p_secret` and starts with `_auth_ok(p_user_id, p_secret)`; a wrong or missing secret raises `UNAUTHORIZED`, and the app then clears its saved login and returns to the first screen. Each secret-version only checks the secret and then calls the older function of the same name (no rule is copied there); the OLD versions (no `p_secret`) are locked from `anon`/`authenticated`. Sign-up refuses names containing admin, support, official, moderator, customercare, helpdesk, vgc, vgcontact or vgkontact (`_name_reserved`; error `RESERVED_NAME`). Known limit: while `require_android_id` is `false`, `login_account` gives the secret to anyone who types the phone number, so the secret protects against leaked user ids (for example from referral lists), not against someone who knows the phone number.
12. **Days are Nigerian days (added 2026-10-04).** A repost "day", today's repost/verify status, the weekly and monthly leaderboards, the daily reminder check and the admin notification stats all use `public._today_ng()` (`Africa/Lagos`, UTC+1), so the daily repost resets at midnight Nigerian time (before: 1:00 am, because UTC was used). `daily_reposts.repost_date` defaults to the Nigerian date. Rows written before the change keep their stored date. SQL: `supabase/migrations/use_nigeria_time.sql`. Timestamps are still stored in UTC; cron schedules are still UTC.

## 4. Tables (public schema)
- `users`: id, android_id, username, phone, referred_by, created_at, total_downloads, total_reposts, last_synced_at, subscription_status, key_balance (unused), fcm_token, is_banned, ban_reason, fcm_token_updated_at, notifications_enabled, notifications_enabled_at
- `contact_groups`: id, group_number, member_count, is_full, is_published, created_at, filled_at
- `contact_group_members`: id, group_id, user_id, username, phone, member_position (smallint, no upper limit), created_at, joined_via (`signup` or `added`)
- `daily_reposts`: id, user_id, repost_date, phone, status (`pending`/`verified`/`rejected`), verified_at, created_at, `kind` (`verify`/`repost`, default `repost`; unique per user, date and kind)
- `app_settings`: key, value
- `banned_identities`: user_id, phone, android_base, reason
- `notifications`: id, user_id (null = broadcast), title, body, is_sent, created_at, action, target, sent_by_admin, fcm_sent, fcm_failed
- `system_contacts` (added 2026-10-04): id, name (empty = default name), phone, sort_order, is_active, created_at. Extra numbers every user's phone saves like the admin/status numbers (plain name, no VGC tag). Default name = setting `system_contact_default_name` (fallback "VGContact"). RLS on, no policies.
- `contact_removals` (added 2026-10-07): id, phone, created_at (unique on the last 9 digits). The delete list: numbers every phone deletes on its next sync (any name, tagged or not). RLS on, no policies.
- `notification_reads`, `notification_receipts` (delivered/opened tracking), `activity_logs`
- Views: `notification_reach`, `notification_stats`

## 5. Settings (`app_settings`)

Optional: `anon_phone`, `admin_contact_name`, `anon_contact_name`.

## 6. Database functions
All are `SECURITY DEFINER` and read-only unless noted.

**Helpers (internal, not callable by the app):** `_ref_match`, `_group_size`, `_repost_cap`, `_setting_int`, `_android_id_required`, `_is_admin`, `_is_banned`, `_is_verified`, `_count_referrals`.

**Writes:**
- `_place_user_in_group(user)`: default-group placement (advisory lock `vgcontact_group_placement`; lowest group with `is_full = false`, creates one if none; only signups count toward `member_count`/`is_full`; does nothing if the user already has a default group). Now called only by trigger function `_place_on_verify`, not at signup.
- `_catch_up_group_grants()`: cron catch-up, calls `_grant_next_group` once per missing group, returns attempts (internal, not granted to anon).
- `_grant_next_group(user)`: adds the user to the lowest full group they are not in (`joined_via='added'`).
- `_verify_repost(user, date)`: returns `no_pending_repost`, `cap_reached` or `verified`; on verify it calls `_grant_next_group`.
- `register_account(p_android_id, p_username, p_phone, p_referred_by)` and `login_account(p_phone, p_android_id)`: what the app calls now. They block reserved names, call `register_or_fetch_user` / `login_by_phone` below, then create the account secret if missing and return it as the extra column `secret`. The two older functions are locked from the app key.
- `register_or_fetch_user` (not callable by the app any more): validates, auto-numbers duplicate usernames (chidera → chidera2), inserts the user (no group yet). Phone format is 11 digits starting with 0.
- `submit_daily_repost(p_user_id, p_kind default 'repost')`: returns `OK`, `ALREADY_REPOSTED_TODAY` (per kind), `REPOST_LIMIT_REACHED`, `ALREADY_VERIFIED` (kind `verify` by a verified user), `NOT_VERIFIED` (kind `repost` by an unverified user), `BAD_KIND` or `USER_NOT_FOUND`. `get_today_repost_status` reads `repost` rows, `get_today_verify_status` reads `verify` rows.
- `record_sync(user)`: stamps `users.last_synced_at` (called by `ContactSync.run` after every successful sync: button, first run, resume, background; opening the app does not count). Helpers `_inactive_after_days` (setting `inactive_after_days`, default 30) and `_is_inactive`.
- `save_fcm_token`, `report_notifications_enabled`, `mark_notifications_read`, `record_notification_delivered/opened`.
- `send_daily_repost_reminder`: inserts reminder notifications (run by cron).
- `send_pending_verify_nudge()`: pushes "Claim your free viewers" (action `open_repost`) to users with a push token, not verified, signed up 24h to 30 days ago (`pending_nudge_after_hours`, default 24), at most once per 3 days. Internal, not granted to anon.

**All functions below that take a user id (`get_app_bundle`, `get_home`, `get_sync_contacts`, `get_removed_numbers` (added 2026-10-07: every number on the delete list, no exceptions; the app also never saves them again), `get_my_profile`, `get_my_referrer`, `get_my_referrals_full`, both referral and repost leaderboards, `get_leaderboard`, `get_today_*_status`, `open_notifications`, `mark_notifications_read`, `submit_daily_repost`, `save_fcm_token`, `record_sync`, `record_notification_delivered/opened`, `report_notifications_enabled`) now also take `p_secret` (rule 11). Where this guide shows an older argument list, add `p_secret` as the second argument.** `get_ban_status` and `get_app_update` stay open (needed before login, nothing private). `get_app_setting` only answers for `community_link` and `update_url`.

**Reads used by the app:** `login_account` (was `login_by_phone`), `get_home`, `get_sync_contacts`, `get_my_profile`, `get_leaderboard` (called by the Repost leaderboard tab: metric `reposts` only, period `all`, limit 50; other metrics raise INVALID_METRIC, and `user_id` is returned only on the caller's own row), `get_my_referrals_full` (list + `is_verified`; wraps `get_my_referrals`), `get_repost_leaderboard_phone` (Repost leaderboard with username and phone; the app falls back to `get_leaderboard` if it is missing), `get_referral_leaderboard_phone` (leaderboard, returns username and phone; the app falls back to `get_referral_leaderboard` if it is missing), `get_referral_leaderboard`, `get_app_setting` (no longer called by the app since 2026-10-03: the settings come in `get_app_bundle`), `open_notifications` (Notifications screen: returns the list, then marks everything read; wraps `fetch_notifications` and `mark_notifications_read`).

**One call for Home and Repost:** `get_app_bundle(p_user_id, p_phone, p_android_id, p_current_build)` returns one row `{bundle: jsonb}` with `home` (what `get_home` returns, null if the user is missing), `has_unread` (bell dot), `banned` + `ban_reason` (from `get_ban_status`), `update` (from `get_app_update`), `community_link` (the `community_link` setting), `today_repost_status` (from `get_today_repost_status`, null = nothing logged today), `settings` (the pending-sheet and pay settings) and `today_verify_status` (from `get_today_verify_status`). It only composes those existing functions, so every rule stays defined in one place; they stay in the database. The app calls it from `SupabaseClient.fetchBundle`: Home makes 1 call per open (was 5), Repost makes 1 per open (was 4). `login_by_phone`, `get_sync_contacts`, `get_my_profile`, the leaderboards, `get_my_referrals` (now `get_my_referrals_full`: list + pending flag in one call) and the notification list (now `open_notifications`: list, then mark-read, in one call) still have their own calls. `get_ban_status` is also called directly by the banned screen.

**Admin only (checked by `_is_admin()`):** `admin_list_system_contacts`, `admin_add_system_contact`, `admin_update_system_contact`, `admin_delete_system_contact` (the extra contacts list, added 2026-10-04), `admin_add_removal`, `admin_list_removals`, `admin_cancel_removal` (the delete list, added 2026-10-07), `admin_find_users`, `admin_pending_reposts`, `admin_set_repost` (verify or reject), `admin_set_banned`, `admin_get_settings`, `admin_set_setting`, `admin_send_notification`, `admin_notification_history`, `admin_notification_stats`, `admin_notification_reach`. Also defined but not used by the admin page: `admin_verify_reposts` (bulk verify by username, with preview) and `admin_add_user_to_group`.

## 7. Automatic things
- **Triggers:** `place_on_repost_verified` (AFTER UPDATE on daily_reposts when status becomes `verified`; places the user in a group); `a_block_signup_when_closed` (BEFORE INSERT on users, honours `registrations_open`); `on_repost_status_change` (AFTER UPDATE on daily_reposts, creates "Repost verified" or "Repost rejected" notifications); `on_notification_created` (AFTER INSERT on notifications, calls the `send-push` edge function); `trg_group_member_removed` (AFTER DELETE on contact_group_members, added 2026-10-07: if the person is in no other group and their number is in `system_contacts`, it switches the number off there and adds it to `contact_removals`).
- **Push:** needs the secret `service_role_key` in Supabase Vault (confirmed present 2026-09-30). If it is missing, pushes silently do nothing.
- **Cron:** `daily-repost-reminder` runs at `0 8 * * *` (08:00 UTC, 09:00 Nigeria time). `catch-up-group-grants` runs once a day at `0 6 * * *` (06:00 UTC, 07:00 Nigeria time). `pending-verify-nudge` runs once a day at `0 16 * * *` (16:00 UTC, 17:00 Nigeria time). `sync-reminders` runs once a day at `0 9 * * *` (09:00 UTC, 10:00 Nigeria time) once `add_sync_visibility.sql` has been run.

## 8. Permissions gotcha (important)
The app connects as the `anon` role and can only run functions it has `EXECUTE` on. A new or recreated function may lack it. Symptom: the call fails silently and the screen shows placeholders. Fix:
```sql
grant execute on function public.<name>(<args>) to anon, authenticated;
notify pgrst, 'reload schema';
```
Since 2026-10-03 the app-callable functions are the ones with `p_secret` (plus `register_account`, `login_account`, `get_ban_status`, `get_app_update`, `get_app_setting`); a function recreated WITHOUT `p_secret` must not be granted to `anon`. The last query in `add_user_secret.sql` lists what `anon` can run. Check with `has_function_privilege('anon', p.oid, 'execute')`. Internal helpers (names starting with `_`) should stay locked. On 2026-09-30, `get_home` and `get_sync_contacts` were missing this and were granted.

## 10. Android app map (`app/src/main/java/com/vgcontact/app`)
- `SupabaseClient.kt`: every server call (`rpc("name", params)`); reads `SUPABASE_URL` and `SUPABASE_ANON_KEY` from BuildConfig. `rpc()` adds `p_secret` to every function in `SECRET_RPCS` and, on `UNAUTHORIZED`, clears the saved login and opens the first screen. `SessionManager.isLoggedIn()` needs both a username and a secret, so an account saved by an older build logs in again once.
- `HomeActivity`: (an amber **pending banner** shows while the `home` status from `get_app_bundle` is `pending`: a CLAIM button; tap brings back the pending (verify) sheet (`PendingPrompt.showGate`), whose button posts the invite image and logs a `verify` row. The Repost screen is for verified users: its button opens the admin's WhatsApp and logs a `repost` row. User-facing wording avoids the word "group"; it disappears once verified. A banner under the header warns when Contacts or Notifications are off, or battery saver may stop sync; tap fixes the first problem; Contacts and battery are ignored while syncing is paused) Free/Extra/Referred viewers (from `get_app_bundle`; the same single call also sets the bell dot, runs the ban check, feeds the update pop-up and saves the community link), Sync Contacts, a referral link row inside the green header card (label above, full link that slides sideways, white Copy button, all in a see-through bordered box; link = `ReferralActivity.LINK_BASE` + phone), Buy Status Viewers. Starts at 0 and /0; shows a toast if loading fails. The free-viewers progress bar was removed (numbers only).
- `RepostActivity` (header has a My Repost / Leaderboard switcher. Leaderboard tab = VGKontact-style single card: column header, numbered rows (gold/silver/bronze badges for 1-3), 10 per page, own row tinted "You"; a Phone number / Username switch in the column header (default Username); data from `get_repost_leaderboard_phone`, falling back to `get_leaderboard`, metric `reposts`), `ReferralActivity` (laid out like VGKontact's Referrals page: header with a My referrals / Leaderboard switcher and search; My referrals = code card + referral list with tap-to-drill-in to levels 2 and 3, rows with invites open, level 3 is the last; Leaderboard = top 50 by direct referrals, a Phone number / Username switch in the column header shows either one; it is linked to the Number / Username switch on the code card (flip one, the other follows; default Number); search matches both; data from `get_referral_leaderboard_phone`; banned users hidden; 10 per page; no Back arrow, but phone Back goes up one level while drilled in), `ProfileActivity`, `NotificationsActivity`, `LoginActivity`, `RegisterActivity`, `SessionManager` (stores `user_id`), `ContactSync` (writes contacts to the phone), `SupportContact.kt`, `LegalContent.kt` (Terms and Privacy, rewritten for groups and reposts).
- `DailySyncWorker.kt`: background contact sync, every ~24 hours by default (WorkManager); Profile > **Sync every N hours** lets the user pick 1, 6, 12 or 24 (stored in `SyncPrefs`, applied with `DailySyncWorker.reschedule`; kept across logout), scheduled from `VGApp`. Same `ContactSync` as the Sync button. Skips when logged out, banned or paused. Contacts permission off gives one reminder notification. Offline or server failure queues a one-time retry that fires when the network returns. New contacts added gives a notification like "3 contacts synced today at 10:30" (nothing is shown on Home). With data off, the sync waits and runs, with the notification, as soon as data is back.
- `SyncPrefs.kt`: local paused flag (`vgc_sync` prefs). Profile > **Delete My Contacts** removes every `VGC<N>` contact and pauses all syncing (button, first-run, background); the same button becomes **Resume Syncing**, which unpauses and syncs at once. Pause is local only, not reported to the database.
- Build: GitHub Actions (`.github/workflows/deploy.yml`, `gradle assembleRelease`) using secrets `SUPABASE_URL` and `SUPABASE_ANON_KEY`; signed with the release keystore when `KEYSTORE_BASE64` (and its password/alias secrets) exist, otherwise the debug key. How zips are deployed: `incoming/DEPLOY_WORKFLOW.md`.
- UI convention: green top, white bottom, Poppins font.

## 11. Admin dashboard (`index.html`)

## 12. Test loop (expected results)
1. Register users 1 to 4: all pending, Free 0/3, no group rows, phones sync only admin/anon.
2. Users 1, 2, 3 each repost; admin verifies each. After the first: group 1 exists with 1 member; after the third: group 1 is full and each shows Free 3/3.
3. Verify user 4: lands in group 2, shows Free 1/3; Sync Contacts on users 1 to 3 adds nothing new from group 2.
4. A verified user gets a "Repost verified" push; the next sync adds their group mates.
